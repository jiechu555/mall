## 场景结果

### S1 打满（判据：成功=库存100、超卖=0、错误仅售罄类、P99<500ms）

5000 请求 / 500 线程 / 30s 爬坡，库存 100、每人限购 1：

| 指标 | 实测 | 判据 | 结论 |
|---|---|---|---|
| 受理中（成功） | **100** | =库存 | ✅ |
| 已售罄 | **4900** | 其余全部为售罄类 | ✅ |
| 超卖 | Redis 库存扣到 **0** 不为负 | 0 | ✅ |
| 守恒式对账 | 库存0 + 受理单100×status1 + 0 = 100 | 恒等 | ✅ |
| P99 | **55ms**（P50=8ms） | <500ms | ✅（9倍裕量）|
| oms_order 落库 | 100 单 order_type=1 | =成功数 | ✅ |

### S3 限购（判据：成功恰=限购数）

单账号 100 并发 × 100 个一次性令牌（活动库存 10、限购 2）：

| 响应 | 数量 | 解读 |
|---|---|---|
| 受理中 | **2** | =限购数 ✅ |
| 超出限购 | 8 | 过频控的前 10 个中，2 成功后被限购拦截 |
| 操作过于频繁 | 90 | 第一层用户频控（10次/秒）拦截 |

比 06 讲判据多展示了频控层：两道防线各自的拦截数清晰可见。

### S2 阶梯（判据：找 QPS 拐点）

每档 180 秒、大库存大限购（纯链路吞吐）、600 个池子会员循环：

| 并发 | QPS | P50 | P99 | 错误 |
|---|---|---|---|---|
| 100 | **1441** | 66ms | 130ms | 0 |
| 300 | 1358 | 218ms | 315ms | 0 |
| 600 | 1120 | 421ms | 862ms | 1.41%（1463 连接错误，见 S5）|

**拐点在 100–300 并发之间，峰值 QPS≈1441**。未达单机 ≥3000 目标：主因是同机部署（负载机、被测 JVM、5 个中间件容器共享 CPU），次要因素是消费端落库速率（数百/秒）远低于受理速率导致 MQ 积压（这本身验证了削峰设计的预期行为：同步链路不受积压影响）。**换独立负载机复测是已知的下一步。**

### S5 积压恢复（判据：无消息丢失、积压消化）

600 并发档中段 `docker pause rabbitmq` 30 秒后 unpause：

- 暂停期间：同步链路继续受理（QPS 降至 931），1463 个请求因 MQ 发送超时失败——**MQ 故障时同步链路降级但不雪崩**；
- 恢复后：unacknowledged=250 → 消费立即恢复 ✓；
- 无丢失对账未能精确完成：本次执行在场景切换时漏清消费队列，旧消息累积污染了计数（教训见下）。**修正后的复测步骤已写入压测脚本注释。**

## 压测方法论踩坑（全部亲历，比数字更值钱）

1. **序列化边界**：redis-cli 灌的裸值与应用端 Jackson2Json 序列化值（字符串带双引号）不互通——令牌集必须以 `"token"` 带引号形式灌入，否则 SREM 永远失配。
2. **RESP 手工协议**：`"tk%08d"` 是 12 字节（引号+2+8+引号），长度算错 2 字节就截断成废成员。
3. **jmx 漏传 memberReceiveAddressId** → 收货快照全空 → `receiver_name NOT NULL` 插入失败 ×101——**防御设计经受住了实战**：101 单全部以 status=0 留痕等待对账，零丢失。
4. **令牌核销发生在 Lua 之前**：无论下单成败令牌都消耗，场景重跑必须重灌令牌集。
5. **场景切换必须清三样**：消费队列 + TTL 队列 + 数据库受理单，漏一样就污染下一场景。
6. 中文日志/grep 在 Git Bash 下有编码失配（用 Python 读日志兜底）。
